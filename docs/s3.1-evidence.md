# S3.1 — macOS Keychain boundary evidence

Date: 2026-08-14. Baseline: `main cdfa8f2`.

Independent security/acceptance audit: **PASS** after two corrections; no open
audit blockers.

## Result

- Added a Core credential-vault boundary for store/read/revoke/status with only
  masked UI states: `NOT CONFIGURED`, `STORED`, `UNAVAILABLE`, `DENIED`, `ERROR`.
- Added a macOS implementation using `Security.framework` SecItem APIs. Secrets
  are not passed through argv, environment, files, settings, journal, UI or audit.
- Keychain items use a namespaced service/account in the user's default local
  file-based login keychain; overwrite is explicit and revoke is idempotent. No
  synchronization, explicit accessibility or `ThisDeviceOnly` claim is made.
- Secret leases and temporary store buffers are cleared where managed memory
  permits. Audit records contain identity, state and reason but no secret value.
- Desktop shows a compact masked `MEXC API` status only. No credential-entry
  fields, private exchange calls, trading transport or orders were added.
- S2.3 safety behavior was not changed.
- Security-audit corrections: successful/missing revoke maps to `NotConfigured`;
  framework handles and native symbols are resolved once per process; store/read
  enforce a documented 16 KiB local safety cap and fail closed on invalid native
  read pointers/lengths.
- Persistent credential audit now stores an allowlisted state code, never an
  arbitrary adapter reason. A two-step, eight-second revoke presentation requires
  `Stored` plus STOP engaged and invalidates on state/STOP/expiry.
- `AuditedCredentialVault` now wraps the actual desktop vault used by startup
  status and revoke. Its bounded audit records all four operations using only a
  validated identity, action, state and allowlisted code; secret and result reason
  are never retained. Undefined venue values fail identity validation.

## Open evidence and risk

- Signed-app gate on 2026-08-14: first allowed smoke returned
  `STORE=Error/InvalidParameter/SecItem` and cleanup
  `REVOKE=Error/InvalidParameter/SecItem`. Per the evidence-backed authorization,
  `kSecAttrAccessible` was removed from the default file-based add query. The one
  permitted final signed-app smoke with a new identity returned the same masked
  categories and exit `2`. These in-sandbox results were later superseded by the
  external acceptance evidence below. The revoke UI remains visually unverified.
- Read-only/interop follow-up: framework/symbol/CFString/CFData/CFDictionary
  diagnostic passed without any SecItem call. Allowlisted failure codes/stages
  were added. Evidence: [`s3.1-native-diagnostic.md`](s3.1-native-diagnostic.md).
- Exact dictionary audit passed: counts, exact keys, CF value types and retained
  lifetimes match; local Apple SDK signatures match the P/Invoke declarations.
  No SecItem call was made and no further smoke was run.
- Phase R native Objective-C signed-app reference reproduced
  `ADD=INVALID_PARAMETER` and cleanup `DELETE=INVALID_PARAMETER` (exit `2`) with
  the minimal default file-based contract. This proves the blocker is not specific
  to the C# dictionary/P/Invoke boundary; no adapter replacement was attempted.
- Independent external gate (outside the Codex sandbox) ran the current signed C#
  harness exactly once: `STORE=Stored/None/SecItem`,
  `READ=Stored/None/SecItem/MATCH=YES`,
  `REVOKE=NotConfigured/None/SecItem`, exit `0`. The native Objective-C reference
  also passed add/read/delete outside the sandbox. Root cause of the earlier
  `InvalidParameter` evidence is therefore the Codex sandbox, not macOS Keychain,
  the query shape or C# interop. Native S3.1 acceptance: `PASS`.
- No real keys, private API, network orders or money path is present.
- S3.2 was not started. The verified S3.1 changeset is recorded by its local
  commit; the exact hash is stored in Git history. GitHub/push are not performed.
