## Официальные источники

- MEXC Spot V3 API: https://mexcdevelop.github.io/apidocs/spot_v3_en/
- Официальные protobuf definitions: https://github.com/mexcdevelop/websocket-proto
- MEXC WebSocket replacement announcement:
  https://www.mexc.com/en-NG/announcements/article/mexc-v3-websocket-service-replacement-announcement-17827791522393

Подтверждено: REST `exchangeInfo` и `depth`; бинарный Protobuf WebSocket
`wss://wbs-api.mexc.com/ws`; канал aggregated depth 100 ms; абсолютные количества;
нулевое количество удаляет уровень; initial bridge допускает покрытие snapshot
первым `[fromVersion,toVersion]` или точную смежность `fromVersion=snapshot+1`;
затем `fromVersion == previous toVersion + 1`;
reconnect/resubscribe обязателен, соединение ограничено 24 часами; до 30 подписок,
100 WebSocket requests/s, public REST limit считается по IP.

## Реализовано и проверено детерминированно

- metadata parser: quote precision -> tick, baseSizePrecision -> quantity step;
- REST snapshot parser;
- минимальный forward-compatible protobuf decoder официальных wrapper/aggre-depth полей;
- bounded pre-snapshot buffer (2048), 1 MiB WS message cap, symbol isolation;
- price > 0, quantity >= 0, quantity=0 deletion marker;
- snapshot/delta bridge, continuity gap -> resync, reconnect reset;
- клиент с REST snapshot и публичной WS подпиской без credentials.

## Live smoke

- Публичный `exchangeInfo` успешно вернул APTUSDT и BTCUSDT metadata.
- WebSocket подключился и перешёл в `WaitingForSnapshot`.
- Два ограниченных smoke run завершились одинаково: полученные live REST/WS версии
  не образовали допустимый bridge; клиент честно перешёл в `Reconnecting` с
  `MEXC order-book continuity lost; reconnect/resnapshot required`, затем test
  timeout 20 s.
- Это не filesystem/sandbox и не отсутствие сети. Диагностика ниже локализовала
  и устранила слишком строгую проверку initial boundary.

### Единственный диагностический smoke

Разрешённый одиночный connection attempt без reconnect loop дал:

- subscription ack: `id=0`, `code=0`,
  `msg=spot@public.aggre.depth.v3.api.pb@100ms@APTUSDT`;
- endpoint/channel/symbol: `wss://wbs-api.mexc.com/ws`, aggregated depth 100 ms,
  `APTUSDT` — совпадают с подпиской;
- REST `lastUpdateId`: **6959267713**;
- первый WS message: `fromVersion=6959267714`,
  `toVersion=6959267734`, `sendTime=1786352127257`;
- точная исходная ветка: **from-greater-than-snapshot**;
- `Engine.TryApplyDelta` не вызывался; post-bridge gap отсутствовал;
- после первого доказанного mismatch клиент остановился (`maxConnectionAttempts=1`).

Фактический live поток начал диапазон ровно с `snapshot + 1`: snapshot содержит
состояние по свою версию включительно, а delta начинается со следующей версии;
данные между ними не пропущены.

После диагностического вывода initial bridge уточнён минимально: допустимо
покрытие snapshot диапазоном либо точная смежность
`fromVersion == snapshot.lastUpdateId + 1`. Значение `snapshot + 2` и больше
остаётся gap; после bridge сохраняется строгое
`fromVersion == previous.toVersion + 1`.

Финальный одиночный acceptance smoke без reconnect loop после этой коррекции:
**PASS**, 1/1, реальные APTUSDT metadata и двусторонний Spot book получены за
4 секунды. Поэтому capability MEXC Spot public market data для стартовых
APT/USDT и BTC/USDT переведена в `Available`.

UI/private API/ордера не добавлялись.

Следующий шаг только после отдельного разрешения: S1.3/UI integration.
